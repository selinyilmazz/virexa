# Cache Components Migration — Scoping Plan

**Status:** not started. This is a plan only — no `next.config.ts` or `layout.tsx` changes have been made. Written because this migration needs a real build (local machine, CI, or a Vercel preview deployment) to verify each step; this sandbox cannot run `next build` at all (see PERFORMANCE_AUDIT.md §6 — `npm install` for the missing Linux SWC binary returns `403 Forbidden` against the npm registry here).

**Why this is needed:** per PERFORMANCE_AUDIT.md, the root layout's `cookies()` reads (auth session + locale) force every route in the app into dynamic (SSR-per-request) rendering, with no partial exception, under the app's current caching model. This is the only Next.js mechanism that fixes that without dropping the no-flash auth/locale UX: enabling `cacheComponents: true` turns on Partial Prerendering, which lets a route emit a static/ISR shell while a small `<Suspense>`-wrapped slice streams in the cookie-dependent part.

**Why it can't be done in one shot:** `cacheComponents` is a single global flag. Per `node_modules/next/dist/docs/01-app/01-getting-started/08-caching.md`, any component that touches uncached dynamic data outside `<Suspense>` or `'use cache'` fails the **build**, not just that route — "Uncached data was accessed outside of `<Suspense>`" is a hard error. Every route in the app has to be correct before the flag can ship, which means this has to be a staged migration with a real build checked at each stage.

## Route inventory (47 pages, 28 API routes, 2 layouts — from `src/app/**`)

**Tier A — already `export const dynamic = "force-dynamic"`, zero risk.** 13 routes already opt out of static rendering explicitly: `/admin` (+ `/admin/audit`, `/admin/runtime`), `/developer-hub` (+ `/tools`, `/roadmaps`, `/courses`, `/learning-paths`, `/cheat-sheets`, `/certifications`, `/github`, `/github/[slug]`), `/open-source` (+ `/topics`), `/api/cron/news-fetch`, `/api/cron/ai-enrichment`. Enabling `cacheComponents` doesn't change these — they were already told to skip static generation, on purpose, for reasons unrelated to the layout bug (e.g. `/open-source`'s doc comment: admin edits should show up on the next request, not the next deploy). No action needed to avoid a build break here; worth a follow-up pass later to see if some of these can move to `revalidate` + `revalidateTag` instead of full `force-dynamic` now that Cache Components makes tag-based invalidation available, but that's an optimization, not a migration requirement.

**Tier B — auth-gated, must stay dynamic, by design.** `/admin/*` (all remaining admin pages — `AdminLayout` itself calls `requireAdminUser()`, which reads the session, ahead of every admin page), `/profile`, `/settings`, `/bookmarks`, `/reading-history`, `/signin`, `/signup`, `/forgot-password`, `/update-password`, `/maintenance`. These should be wrapped correctly (their auth check needs to be inside `<Suspense>` per the Cache Components model) but are never expected to become static — that's correct, not a regression.

**Tier C — real static/ISR candidates.** `/` (home), `/article/[slug]`, `/category/[slug]`, `/news`, `/search`, `/most-read`, `/cloud`, `/resources`, `/categories`, `/about`, `/privacy`, `/terms`, `/cookies`, `/developer-hub/releases`, `/developer-hub/releases/[slug]`, `/developer-releases`. This is where the invocation-count reduction actually comes from — these are the pages that should end up with a static or `revalidate`-backed shell once the migration lands. `/about`, `/privacy`, `/terms`, `/cookies` in particular have no per-request data at all and should become **fully static** (zero Function invocations, ever, until the next deploy) — currently they're paying the same full-dynamic cost as everything else purely because of the shared root layout.

**API routes (28 `route.ts` handlers).** Per the Cache Components docs, `GET` route handlers follow the same prerendering rules as pages once the flag is on. Of the 28, the large majority are `POST`/`PATCH`/`DELETE` admin-mutation endpoints (unaffected — mutations are never static). The one worth checking explicitly is `/api/admin/notifications` (`GET`, polled every 90s by `NotificationsBell.tsx`) — it must stay dynamic (it's real-time-ish, admin-only, low volume) rather than accidentally getting cached.

## Phased plan

**Phase 0 — environment.** Get a build-capable environment wired up before touching any app code: your machine (`npm run build`) or a Vercel preview deployment tied to a feature branch. Nothing in Phase 1+ should be attempted without one of these — that's the whole reason this stayed a plan instead of a diff in this pass.

**Phase 1 — flip the flag, fix the root layout first.** `cacheComponents: true` in `next.config.ts`, then split `src/app/layout.tsx`:
- Extract the `supabase.auth.getSession()` call into a small child Server Component, wrapped in `<Suspense>` so it streams instead of blocking the shell — this is a clean win, directly achieves goal 2 ("smallest possible subtree").
- Locale is the harder case: `resolveServerLocale()`'s result sets `<html lang={locale}>` on the layout's own root element, which is an ancestor of any `<Suspense>` boundary — it structurally cannot be deferred into a suspended child without either (a) shipping a default `lang="en"` in the static shell and correcting it after the locale slice resolves (a small, real behavior change — a brief incorrect `lang` attribute, not visible text, but still a change), or (b) leaving locale resolution in the blocking part of the layout, which keeps the whole shell dynamic and defeats the purpose. This is a real product decision, not an engineering detail — flag it for explicit sign-off during implementation rather than picking silently.

**Phase 2 — data layer.** Add `'use cache'` + `cacheLife(...)` + `cacheTag(...)` to the read functions backing Tier C pages: `getArticleDetail`, `getFeaturedArticle(s)`, `getActiveCategoryCounts`, `searchCategoryArticles`, `getRecentArticlesForCategory`, `getTopSourcesForCategory`, `getLatestArticles`, `getLatestReleases`, `getResourcesNews`, `getReleaseDetail`, `getReleaseLibrary` (all in `article-read-service.ts` / `release-detail-service.ts`). Tag by slug/category (e.g. `cacheTag(`article:${slug}`)`) so an admin edit (`/admin/articles`, `/admin/releases`) can call `updateTag()` for instant invalidation instead of waiting out the revalidate window — this is what makes the admin-freshness property `/open-source`'s `force-dynamic` was protecting still hold true under ISR.

**Phase 3 — page-by-page build validation.** Work through Tier C one route at a time, running a real build after each: fix whatever "accessed outside Suspense" errors surface (usually one of: a component reading `searchParams` outside a boundary, an uncached fetch, or a personalized bit like `isBookmarked` that needs to move behind its own `<Suspense>` or become a client-side check post-hydration). Tier A and B need the same audit but should require little to no code change since they're either already `force-dynamic` or correctly gated behind an auth check.

**Phase 4 — QA checklist before shipping.**
- Build completes with zero blocking-route errors.
- `next build`'s route summary shows the expected Tier C routes as static/ISR (○/prerendered), Tier A/B as dynamic (ƒ) — confirms the migration did what it was supposed to, not just that it compiled.
- Manual pass: sign-in/sign-out (no header flash regression beyond what Phase 1 explicitly signed off on), language switch still applies immediately, Maintenance Mode still takes effect immediately (unrelated to this migration — it's middleware-level, not layout-level, but worth re-confirming), admin edits to an article/release/repository show up within the configured `revalidate` window or immediately via `updateTag`.
- Watch the Vercel Function Invocations graph for 24–48h on the preview/staging deployment before promoting.

## What to expect once this ships

Per PERFORMANCE_AUDIT.md's mechanical estimate: every request to the same Tier C path within its `revalidate` window (60s, already configured on article/category) collapses to at most one render invocation instead of one per request. `/about`, `/privacy`, `/terms`, `/cookies` should drop to effectively zero invocations (fully static). The actual aggregate drop in the 49,000-invocation figure depends on how concentrated real traffic is on repeat paths within those windows — that's only visible in your Vercel traffic logs, not the codebase.
